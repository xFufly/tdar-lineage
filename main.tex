\begin{abstract}
\noindent
Data lineage is a critical aspect of modern data management, providing insights into the flow and transformation of data across complex ecosystems. This paper introduces the T-DAR framework, a dynamic approach to analyzing data lineage that emphasizes the relationship between targeted observations, data assets, and actionable results. By leveraging the T-DAR framework, organizations can enhance their understanding of data processes, improve decision-making, and ensure compliance with regulatory requirements.
\end{abstract}

\section{Introduction}
In the era of Big Data, organizations have adopted a data-driven approach to decision-making. However, the complexity of data ecosystems often leads to challenges in understanding the flow and transformation of data \cite{syed2020}. This paper introduces the \textbf{T-DAR framework}, which stands for Targeted Data-Actions-Results, as a methodology for analyzing data lineage and ensuring actionable insights. 

The T-DAR framework provides a structured approach to capturing and analyzing the relationships between data assets, the actions taken on them, and the resulting outcomes. By focusing on targeted observations, organizations can gain a deeper understanding of their data processes and make informed decisions based on actionable insights.

\section{T-DAR Framework Overview}
The T-DAR framework is inspired by the Data-Action-Response (DAR) model of most healthcare information systems \cite{portableRN2007}.

\subsection{Architecture}
As illustrated in Figure \ref{fig:tdar_architecture}, the architecture of the T-DAR framework is centered around a \textit{Targeted Observation}, which is directly linked to a specific \textit{Data Asset} within the ecosystem. Rather than treating data lineage as a static representation of data streams, the T-DAR framework takes advantage of the dynamic nature of data environments, allowing for real-time analysis and decision-making. It provides a way to analyse not only results, but also the medium through which the results are obtained, and the actions that lead to those results.

To operationalize this dynamic analysis, every \textit{Targeted Observation} acts as a container for a chronological sequence of \textit{DAREntry} records. These entries are categorized into three distinct phases:
\begin{itemize}
    \item \textbf{Data (D) -- The Assessment:} A Data entry represents a factual snapshot, an audit trail, or a metric collected from the \textit{Data Asset}.
    \item \textbf{Action (A) -- The Intervention:} An Action entry represents a specific action taken in response to the data or the results of the data.
    \item \textbf{Result (R) -- The Outcome:} A Result entry represents the outcome or consequence of the preceding action taken.
\end{itemize}

As shown in Figure \ref{fig:tdar_state}, these DAR entries act as triggers that drive the lifecycle of a \textit{Targeted Observation}, transitioning it from an initial open state to a final resolution.

Furthermore, since data assets are inherently interconnected through a \nolinkurl{derived_from} lineage relationship, the T-DAR framework allows organizations to track how an \textit{Action} applied to an upstream asset propagates its \textit{Results} to downstream dependencies. This elevates traditional data lineage from a simple dependency graph to an actionable governance tool.

\subsection{Handling Fine-Grained Lineage}
A critical strength of the T-DAR framework is its ability to manage complex, fine-grained lineage. While traditional models often stop at the table or system level, a \textit{Data Asset} in T-DAR operates as a polymorphic entity. It can represent a macro-level database, a micro-level column, or even a processing function. 

Consequently, an observation simply references a granular identifier, such as \nolinkurl{urn:asset:silver:transactions:transaction_amount}, without altering its own generic data model. This precision ensures that downstream impact analysis is exact, allowing data teams to isolate and resolve granular issues without invalidating or locking entire tables.

\subsection{Core Data Model}
To establish rigorous guarantees on data consistency, T-DAR relies on a structured data model. The system operates over a dependency graph where each asset exposes its downstream impact.

\paragraph{Core Data Structures.}
The framework is built on two primary objects: the \texttt{DAREntry} and the \texttt{TargetedObservation}.

\noindent
\begin{minipage}{\linewidth}
\begin{lstlisting}[language=Java]
struct DAREntry {
    UUID id;
    EntryType entryType;  // DATA, ACTION, or RESULT
    Timestamp timestamp;  // Event execution time
    String agentId;       // Human or AI agent identifier
    JSON payload;         // Contextual data and metrics
}

class TargetedObservation {
    UUID id;
    String dataAssetId;   // URI of the targeted data asset
    String targetType;    // e.g., DATA_QUALITY, SECURITY
    TargetStatus status;  // OPEN, IN_PROGRESS, RESOLVED, OBSOLETE
    List<DAREntry> log;   // Chronological history of events
}
\end{lstlisting}
\end{minipage}

\paragraph{State Machine Lifecycle.}
The lifecycle of an observation is governed by a deterministic state machine:
\begin{align*}
    \text{NULL} + \text{DATA} &\longrightarrow \text{OPEN} \\
    \text{OPEN} + \text{ACTION} &\longrightarrow \text{IN\_PROGRESS} \\
    \text{OPEN} + \text{RESULT} &\longrightarrow \text{OBSOLETE} \\
    \text{IN\_PROGRESS} + \text{RESULT} &\longrightarrow \text{RESOLVED}
\end{align*}
Any transition not explicitly covered by this state machine throws an exception, guaranteeing that no corrective action can be recorded without prior anomaly detection.

To demonstrate practical value, we evaluate the framework within a standard medallion architecture pipeline \cite{databricks_medallion}, structured into Bronze (Raw), Silver (Cleaned), and Gold (Aggregated) layers.

As depicted in Figure \ref{fig:tdar_case_study}, the framework provides end-to-end traceability when an anomaly occurs:
\begin{enumerate}
    \item An automated agent (\textit{Agent\_1}) detects that 5\% of values are missing in the Silver layer and initializes a \textit{Targeted Observation} with a \texttt{DATA} entry.
    \item Upstream-downstream lineage identification instantly warns stewards of propagation risks toward the Gold layer.
    \item A data engineer (\textit{Agent\_2}) executes an imputation pipeline, appended as an \texttt{ACTION} entry.
    \item Automated validation runs and records a \texttt{RESULT} entry confirming 0\% missing values, marking the observation as \texttt{RESOLVED}.
\end{enumerate}

\section{Related Work}
Data lineage specifications such as OpenLineage \cite{openlineage} standardize passive metadata collection across pipeline runs. OpenLineage focuses on capturing job executions, inputs, and outputs to maintain dependency graphs. Observability tools build on this by alerting on data degradation.

However, existing frameworks primarily address anomaly detection (the \textit{Data} phase) without tracking downstream interventions (\textit{Action} and \textit{Result}). T-DAR is designed to complement existing platforms: by running on top of OpenLineage dependency graphs, it connects operational alerts directly to remediation histories.

\section{Conclusion and Broader Applications}
This paper introduced the T-DAR framework, a structured architectural pattern that bridges the gap between static data lineage and active governance. By encapsulating issues within Targeted Observations and tracing the lifecycle through Data, Action, and Result (D-A-R) entries, organizations gain an immutable and actionable audit trail of their ecosystems.

While the primary case study focused on data quality in a medallion architecture, the T-DAR framework is fundamentally domain-agnostic:
\begin{itemize}
    \item \textbf{Marketing and Campaign Tracking:} Documenting marketing initiatives where observations target specific demographics, trace campaign execution, and measure conversion ROI.
    \item \textbf{Hybrid Automated Controls:} Facilitating AI-driven anomaly detection combined with explicit human engineer approval workflows.
    \item \textbf{Universal Process Security:} Securing and auditing operational processes to ensure total accountability regarding who performed an intervention, why it was triggered, and what the final outcome was.
\end{itemize}
